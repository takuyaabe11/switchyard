# ペルソナによるニーズの洗い出し 2 回目(0.12.0・2026-09-24)

## やり方

[1 回目](2026-09-24-personas.md)と同じ。コードを読まない独立したエージェントに、それぞれ 1 人のペルソナを演じさせた。

1. switchyard を知らない状態で、自分の悩みを書く。
2. その後で README だけを読んで答える。

1 回目の 6 人は、0.12.0 で判断が変わるかを見るために同じ設定で聞き直した。前回の答えに引きずられないよう、各エージェントには前回の結果を見せていない。
新しく 2 人を足した。1 人は 1 セッションからサブエージェントを並べる開発者、もう 1 人は導入を審査するセキュリティ担当。

これは本物の利用者の声の代わりにはならない。優先度の仮説を立てるためのもの。

## 8 人と判断

| ペルソナ | 1 回目 | 2 回目 | 決め手 |
|---|---|---|---|
| 個人で SaaS を運営(Mac 16GB・worktree 3〜4 本) | maybe | maybe | 共有の Postgres/Redis と Playwright のポートが一番の悩みだが、既定では効かない |
| monorepo の基盤担当(64 コア・`claude -p` 8 本) | 自分 maybe・チーム no | 自分 yes・チーム maybe | 観察モードと replay で安全に試せる。`claude -p` を大規模に試していないことがチーム展開の壁 |
| ML 研究者(共有 GPU 機) | no 寄りの maybe | no | 一番の悩みは GPU。README に GPU の語が一度も無い |
| モバイル開発リード(xcodebuild・Gradle) | maybe | maybe(yes 寄り) | 環境のせいの失敗の見分けが「一番刺さる」。シミュレータとエミュレータは対象外 |
| フリーランス(WSL2・8GB・Laravel) | no 寄り | maybe(yes 寄り) | PHPUnit・`artisan test`・Pest が対象に無い |
| EM(12 人・dev container・Gradle) | 希望者のみ観察モード | 希望者のみ | 実運用データが無い。`Bash(switchyard run:*)` の許可を説明できない |
| 新: サブエージェント派(Go/Rust・Testcontainers) | — | maybe | サブエージェントに効くか README に無い。docker が対象外 |
| 新: セキュリティ担当(金融) | — | 条件付き承認 | 通信しない・外し方がある点は良い。署名が無く、`SWITCHYARD_OFF` を組織で固定できない |

1 回目より前向きになった人が 3 人いる(基盤担当・モバイル・フリーランス)。後ろ向きになったのは ML 研究者だけで、GPU が無いことが理由。
「怖さ」の指摘(秘密・Stop・git・通信)は 1 回目より明らかに減った。今回は「自分の道具・自分の悩みに効くか」が中心になった。

## 複数人に共通したこと

### README に書けば済むこと(機能はある)

| 質問 | 人数 | 実際 |
|---|---|---|
| 鍵を持ったジョブが異常終了したら鍵は残るか | 3 | 接続が切れるか心拍が途絶えると解放する |
| サブエージェント(Task ツール)の Bash にも効くか | 2 | 効く(hook も PATH の shim も同じ)。replay もサブエージェントの記録を読む |
| 学習した値は repo ごとか、混ざらないか | 3 | repo とプロファイルの組ごと |
| docker compose・DB・シードスクリプトに鍵だけを付けられるか | 3 | `switchyard run --lock db -- …`、または `switchyard.json` の profile で付けられる。例が無い |
| dev container・WSL2 で何を測るか | 3 | その Linux の中(コンテナや WSL の VM)の CPU とメモリ。書いていない |
| 共有機での `SWITCHYARD_CAPACITY`・`reserve` の目安 | 3 | 書いていない |
| settings.json に何が書かれるか | 3 | プラグインの hooks.json で、ユーザーの settings.json には書かない。書いていない |
| Nx の `--parallel`・Bazel のリモート実行との関係 | 1 | 書いていない |

### 指摘された本当の問題

1. **`Bash(switchyard run:*)` の許可は広すぎる(3 人。うち 1 人はセキュリティ担当)。**
   README はこの許可を勧めているが、これを許すと `switchyard run -- <何でも>` が承認なしに通る。0.12.0 の自動の包みで、これを許す人が増える。
   この推奨は、権限の確認を弱める方向に働いている。いちばん急いで直すべき点。
2. **自分の道具が対象外(6 人)。**
   - PHPUnit・`artisan test`・Pest
   - docker compose と Testcontainers(ポートと DB)
   - シミュレータとエミュレータの起動
   - GPU
   - Xcode・Gradle・Bazel・Nx にワーカー数が伝わらない(自分で書く必要がある)
3. **ポートと DB の衝突が一番の悩みなのに、鍵は自分で書く必要がある(5 人)。** 自動で直列にしてほしい人と、worktree ごとにポートを割り振って並列のまま走らせたい人がいる。
4. **実運用データが無い(5 人)。**
   - 数字は 4 コアの 1 台だけ
   - `claude -p` を大規模に試していない
   - 12 人のチームでのデータが無い
5. **組織で統制できない(2 人)。**
   - リリースに署名もハッシュも無い
   - `SWITCHYARD_OFF` を組織で禁止できない
   - 記録は本人が消せる
6. **pause・throttle で止められたテストが、再開後にタイムアウトしないか(3 人)。** 既定は never なので、コンテナを使うテストの注意書きを足せば済む。
7. **放置中に詰まったセッションに気づけない(2 人)。** 1 回目の「通知」の話と同じ。

## 読み取ったこと

- 1 回目の「怖さ」への対処(0.11.0)と、環境のせいの失敗の見分け(0.12.0)は届いている。見分けは 4 人が「刺さる」と答えた。
- 次に効くのは広さ:
  - 自分の道具が既定で対象に入っていること(PHP・docker/Testcontainers)
  - 自分の構成(dev container・WSL2・サブエージェント・共有機)で何が起きるかが README に書いてあること
- `Bash(switchyard run:*)` の推奨は、自分で入れた退行。0.12.0 で包みを自動にしたことで、影響が広がった。
- 全員が、最初の 1 週間は replay と観察モードで試すと答えた。この入口は機能している。
