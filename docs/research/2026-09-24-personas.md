# ペルソナによるニーズの洗い出し(2026-09-24)

## やり方

最初の試みでは、コードを読んだ私(開発に使っている Claude)が 5 人を演じた。その結果は、私が既に知っていた実装の穴を言い直した
だけになった。そこで、コードを一切読まない独立したエージェント 6 つに、それぞれ 1 人のペルソナを演じさせた。

1. switchyard を知らない状態で、自分の仕事と、並列の Claude Code での悩み(頻度・損失・今の回避策)を書く。
2. その後で README(英語)だけを読み、使うか・どの悩みに効くか・怖いこと・100 点に足りないものを遠慮なく書く。

これは本物の利用者の声の代わりにはならない。優先度の仮説を立てるためのもの。

## 6 人と、導入するかの判断

| ペルソナ | 環境 | 判断 |
|---|---|---|
| 個人で SaaS を運営 | Mac 16GB・worktree で 3〜4 本・Next.js・Playwright・Docker | maybe(まず観察モード) |
| 大規模 monorepo の基盤担当 | 64 コア・`claude -p` で 8 本を並列・Bazel/Nx | 自分は maybe、チーム展開は no |
| 大学の ML 研究 | 共有の GPU 機・pytest・長時間の学習 | no 寄りの maybe |
| モバイル開発のリード | Mac 32GB・xcodebuild・Gradle・エミュレータ | maybe |
| フリーランス | Windows+WSL 8GB・ほぼ 1 セッション | no 寄り |
| EM(12 人のチーム) | 社用 Mac・dev container・Gradle | 希望者のみ観察モードで許可 |

## 複数人に共通したニーズ

| ニーズ | 人数 | 0.11.0 での扱い |
|---|---|---|
| 記録のコマンドから秘密を隠す | 6 | 既定で伏せる(`SWITCHYARD_LOG_COMMANDS`) |
| Stop を「知らせるだけ」にできる | 5 | 既定で知らせるだけ(`SWITCHYARD_STOP=block` で差し戻す) |
| git の shim を切れる | 5 | 既定で何もしない(`SWITCHYARD_GIT=1` で鍵を取る) |
| 環境のせいの失敗(タイムアウト・OOM・シミュレータ)を見分けて Claude に伝える | 4 | 次の候補 |
| 待ち・許可待ちに気づける通知 | 4 | 範囲外(未着手) |
| 更新の確認(外への通信)を既定でオフ | 4 | 既定でオフ(`SWITCHYARD_UPDATE_CHECK=1` で有効) |
| worktree ごとのポート・DB の割り当て | 3〜4 | 未着手(範囲の外側) |
| 自分の重い道具への対応(xcodebuild・Bazel/Nx・`./gradlew` を拒否せず包む・Docker/Testcontainers) | 3〜4 | 次の候補 |
| 共有機で他人の負荷を考える | 1 | README に注意を書いた |
| headless(`claude -p`)での挙動と集計 | 1 | README に書いた。集計は未着手 |
| GPU | 1 | 未着手 |

README だけでは伝わらず、誤解されていた点(README に答えを書いた): デーモンは Unix ソケットだけで話す。git の鍵は worktree ごとに別。
空きメモリには Docker やエミュレータの分も入る。`SWITCHYARD_THINKER` という名前の意味が伝わらない(`SWITCHYARD_OFF` にした)。

## 読み取ったこと

- 導入を止めているのは機能の不足より「怖さ」(秘密の残るログ・全コマンドへの割り込み・セッションを止める Stop・勝手な通信)。
- 本当の仕事は「速くする」より「並列のエージェントを信頼できるものにする」こと。環境のせいの失敗をコードのバグと誤解される話は、
  コードから見た私の見立てには無かった。
- 速さの数字への関心は薄く、「4 コアの実験で自分の機械に効くか分からない」という疑いの方が目立った。
- 全員が「観察モードで 1 週間試す」なら受け入れると答えた。
